底下是看完影片後的筆記

  • 什麼是敏捷測試
    • 定義
      • 新玩意?
        • 並不是
      • 敏捷測試本質上還是一種測試，只是適應組織以及敏捷項目開發的一種過程
    • 想達成什麼
      • 適用敏捷開發的測試方法
      • 讓團隊中的每個人都參與到測試過程中，因為測試是軟體開發過程的重要組成部分
    • 敏捷項目的測試方法
      • 獨特(Unique): 可能根據以下的狀況產生不同的方案
        • 公司(Environment)
        • 組織(Organisation)
        • 部門(Department)
        • 團隊(Team)
        • 團隊成員(! Team Member)
      • 適配(Fits): 適配開發過程，因為測試以及開發是緊密結合的過程
        • Merges
        • Maps to Dev Approach
          • 對敏捷項目的測試方法需要一致，因為敏捷項目的測試不再只與測試人員有關
          • 測試是基於項目的，不同的人可以用不同測試方法做不同等級的測試
            • 功能性
            • 效能
            • 壓力測試
            • 安全性
            • 可用性
        • Covers Risks
          • 風險可能在系統的不同地方，因此我們要進行不同的測試來嘗試適應
        • Agreed
      • 調適(Adapts)
        • Changes as process changes
          • 測試方法會因為開發方式改變，試著調適測試方法
        • Changes are risk profile changes
          • 隨著項目推進風險狀況可能會變化
        • To skills on team
          • 團隊的技能會隨著時間的推移而適應
            • 開發者會學習到如何更好的進行測試，因為他們與測試人員一起工作
              • 開發者可以完成的測試工作量會隨著時間的推移而改變
        • To System Architecture
          • 學習不同系統架構以及學習如何測試
            • 測試的不同等級
              • GUI
              • API
              • 二進位協定
        • To timescales
          • 項目會在不同時間點交付功能，某些功能可能橫跨版本以及多的疊代，我們必須適應這一點的方式進行測試
            • 正在進行的項目也需要測試
            • 適應在不同開發階段的測試方法
      • 簡單(Simple)
        • Involve Everyone
          • 讓團隊的同仁都參與測試環節
        • Part of Development
    • 敏捷測試的迷思
      • 變快
        • 如同敏捷開發會被誤以為是追求軟體開發變快
        • 變快的是更快的滿足需求，而測試方法也必須因應做調整
    • 敏捷測試與一般測試的不同
      • 一般測試
        • 測試之前要提前知道所有範圍並產生計畫後產生文件
      • 敏捷測試
        • 不一定事先知道該做什麼
        • 透過排序功能並依照順序做測試
        • 可能會有一些風險
          • 降低風險的方法
            • 舉例
              • TDD
              • ATDD
        • 適應不同的環境(項目所處的開發流程及團隊運作方式等)才是敏捷測試的精神
          • 了解測試的本質並適應環境
            • 本質
              • 找到問題
              • 預防問題
              • 做什麼測試對我們有價值
                • 回饋(feedback)
                  • 將回饋傳遞給誰
                  • 是否根據回饋採取行動
                • 保證(Assurance)
                  • 流程是否內建品質
                • 認證(Certification)
                  • 品質通過是否有某種強制性標準
                    • ISO?
                    • 滲透測試認證?
                • 探索(Exploration)
                  • 是否有什麼是我們沒發現的問題
                • 風險(Risk)
                  • 風險的不同也會影響我們進行測試的方法
          • 測試不是只有測試人員需要掌握的
            • 測試是關於
              • 流程
              • 使用的測試方法
            • 我們如何測試
              • 建立測試模型以及比對系統是否符合
                • 功能性需求測試模型
                • 非功能性需求測試模型
            • 什麼技能(對於測試)是重要的
          • 舉例
            • 瀑布
            • 敏捷
            • Scrum
      • 不同之處
        • Strips away the extras
          • What extras?
            • Test Plan Documents
            • Test Strategy Documents
            • Test Scripts
            • Test Reports
            • Test Management Tools
            • 總結
              • 未必能提前知道所有的測試範圍，即便知道了也可能因時間推移而發生變化
              • 大量的文件不是必需的
        • Why no extras?
          • Extras are a response
            • to the development process
            • to the regulatory requirements
            • to the management process
            • to the offshoring process
            • to the team organisation
          • 總結
            • 測試過程是開發過程的回應
            • 團隊需緊密的合作，測試不該是外包的
  • 總結
    • Adapt
    • Tackle Risk
      • Process
      • Product
      • Technical System
    • Avoid Trappings
      • light weight
      • fast
    • Testing
      • as a verb
      • not a noun

課堂筆記

敏捷測試?

從字面看敏捷測試有 敏捷 & 測試 這兩個詞。
如果讓我用一個名詞來說明對敏捷的理解，我的答案是 調適。

回應環境以及需求的變化，不斷的小步交付並得到回饋後進行調整。

而用一個名詞來說明我對測試的理解，我的答案是 預防。

透過找到問題來避免問題隨著時間不斷地承受甚至擴大了壞的影響。

敏捷測試在講述的是 調適 以及 預防

團隊成員在軟體開發的早期階段以實例化需求確保對業務價值理解一致，並因應項目的交付進行持續的精準測試，
透過持續的精準測試，軟體的開發週期每個環節都做好預防缺陷，才能把品質融入在整個流程中。

傳統測試計畫 V.S 敏捷測試計畫

  • 測試計畫

    • 規範
      • 測試文檔標準 IEEE 829
        • 定義了格式但沒有定義需要全部應用
    • 內容
      • 測試如何完成（包括 SUT 的配置）
      • 誰來做測試
      • 將要測試什麼
      • 測試將持續多久（雖然根據可以使用的資源的限制而有變化）
      • 測試覆蓋度的需求，例如所要求的質量等級

  • 傳統測試計畫

    • 特點
      • 需要了解項目完整範圍才能擬定測試計畫
        • 測試計畫是預先定義的且詳細的
      • 可能僅由測試人員制定
    • 執行上的困難
      • 項目初期很難了解完整範圍，在項目持續推進後也可能發生範圍調整
      • 詳細的測試計畫需要花很多時間撰寫
      • 項目範圍調整後的測試計畫調整的成本可能很高

  • 敏捷測試計畫

    • 特點
      • 測試計畫是一個過程，會隨著項目持續演進及調整
      • 由整個團隊制定測試目標
      • 先寫最重要的事，之後再繼續規劃
    • 執行上的困難
      • 軟體開發週期間須持續執行對應的測試
        • 開發週期需有不同顆粒度的測試計畫
          產品開發週期產品規劃版本規劃疊代規劃每日規劃
          產品規劃的顆粒度主題版本計畫疊代目標每日目標
          對應的測試計畫產品測試計畫版本測試計畫疊代測試計畫持續更新疊代測試計畫
        • 團隊需要有較多的自動化測試來支援測試計畫的執行

敏捷測試象限

  • 第一象限
    • 面向技術支持團隊
    • 開發人員主要執行的測試
      • 測試類型
        • 單元測試
        • 整合測試
      • 測試目標
        • 主要驗證單元及模組是正確的
      • 主要採用自動化測試，在程式碼進到 repo 時跑
  • 第二象限
    • 面向商業支持團隊
    • 測試人員主要執行的測試
    • 測試類型
      • 功能測試
      • 情境測試
      • 用戶故事測試
    • 測試目標
      • 一個功能或使用者故事是否被正確執行
    • 自動化為主手動測試為輔
  • 第三象限
    • 面向商業評價產品
  • 第四象限
    • 面向技術評價產品

課後心得 - 筆記濃縮小結

敏捷測試是一種基於團隊協作的測試實踐。
著重在預防缺陷而非發現缺陷。
無論團隊正在使用瀑布法或敏捷法都可以導入敏捷測試，因為敏捷測試是因應團隊整體狀況調整的。
為了預防缺陷，測試活動會貫穿於研發開始到交付。
測試工作不再是部分團隊成員的工作，品質是所有團隊成員的責任。
組織的配置上測試人員應該要在敏捷項目的開發團隊中而不是獨立於團隊外。
在整個軟體研發的過程中，所有團隊成員都該盡早參與軟體的早期階段，
通過實例化需求來確保對業務價值理解的一致，並與開發人員一同開發以及維護自動化測試。
及早透過不同維度的自動化測試來及早回應開發團隊的持續交付。
像是單元測試、API 測試、 UI 測試以及編譯驗證測試都是自動化測試的一部分。
除了透過自動化測試做持續的測試覆蓋，在產品持續交付的過程中，
測試人員還是會碰到週期變短以及不知道二個交付之間到底改了什麼，導致不知道影響到哪些功能所以無法掌握測試範圍的情形。
藉由精準測試，基於程式碼的變更範圍進行分析，確定改動範圍後進而決定要進行的針對性測試來避免掉可能多於的測試。
幾個有 AHA 的地方

  1. 在導入敏捷測試的開發團隊，測試人員應專注在進行探索測試、整合測試以及對用戶影響大的測試，而開發人員協助已有案例的回歸測試。 而我想團隊不管是怎麼協作的，在敏捷項目中工作的開發人員培養測試思維是必要的。
    David: 測試思維 => 假設一切都是錯的
  2. 開始評估開發流程中導入 Product backlog refinement meeting，並及早讓 RD 和 QA 一同評估 Product backlog。
